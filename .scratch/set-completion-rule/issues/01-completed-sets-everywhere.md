# Count only completed sets in progress, previous results and export

Status: closed
Category: bug

## Context

Volume now counts only **completed work sets** (see `GLOSSARY.md`). Three other places still count every
set that has a weight or reps entered, so **planned sets** (pre-filled by "Add set" or an exercise swap,
never checked off) leak into them:

- Progress graph (`src/lib/actions/exercises.ts`, the `set_entries` query filtered by
  `weight_kg.not.is.null,reps.not.is.null`). Introduced on purpose in 1f7b586 (2026-04-09):
  "show all sets with weight in progress graph regardless of per-set completed flag".
  It also counts **warmup sets** in its volume and falls back to `target_reps` when reps is empty.
- Previous results (`getPreviousResultsInternal`, `src/lib/actions/sets.ts:40`, same rule since 5699a77).
  Not display-only: it drives the suggested weight (`getSuggestedWeightInternal`, `sets.ts:116`) and the
  set count / pre-fill of the next workout (`workout.ts:353`, `workout.ts:641`, `freestyle.ts:534`).
- `getSuggestedWeight` (`sets.ts:103`) counts warmup sets; `getSuggestedWeightInternal` excludes them.
- History export (`exportWorkoutHistory` in `src/lib/actions/history.ts`): per-exercise volume, top set and
  set count use all work sets.

The database PR / progression functions in `supabase/setup.sql` already count only `completed = true`.

## Question to settle before implementing

1f7b586 suggests sets were often not checked off in practice. Switching previous results to completed
sets means an unchecked set from last time is no longer suggested. Decide per place whether to switch,
and whether older workouts need any special handling.

## Done when

- Each of the three places either uses the completed-set rule or has a recorded reason not to.
- Tests cover the planned-set case at whatever seam is agreed.

### Agent Brief (2026-10-24)

> *This was generated by AI during triage.*

**Category:** bug
**Summary:** Move every server-side "which sets count" rule into one set-rules module, applying the
completed-set rule from `GLOSSARY.md` everywhere.

**Current behavior:**
Session volume counts completed work sets, but the progress graph, previous results, suggested weight
and history export each filter sets their own way: planned sets (pre-filled, never checked off) count,
the progress graph also counts warmup sets and substitutes target reps for missing reps, and the public
`getSuggestedWeight` counts warmup sets while `getSuggestedWeightInternal` does not.

**Desired behavior** (terms as defined in `GLOSSARY.md`):
- One in-process module owns: volume, top set, the previous-results selection, and suggested weight.
  `sessionVolume` moves into it. Callers pass set rows in and get answers back; no Supabase access inside.
- Progress graph points (per workout date): top set, volume and set count from completed work sets only.
  Warmups excluded; no target-reps fallback (a set without reps adds no volume).
- History export: per-exercise volume, top set and work-set count from completed work sets only.
- Previous results: completed sets of the chosen entry; if that entry has no completed sets, fall back to
  every set with a weight or reps entered (the lifter forgot to check off). Entry choice (most recent
  finished non-deload workout, same equipment) is unchanged, except an entry qualifies if it has any set
  that the selection would return.
- Suggested weight (both the public and internal variants): computed from previous results' work sets
  only — max weight, +2.5 kg when the number of work sets reached the target, as today.

**Key interfaces:**
- `sessionVolume(sets)`: same contract as now (completed work sets), relocated.
- New pure functions for previous-results selection, top set and suggested weight, consumed by
  `getPreviousResultsInternal`, `getSuggestedWeight`, `getSuggestedWeightInternal`, `getExerciseProgress`
  and `exportWorkoutHistory`. Their return types stay the same.

**Acceptance criteria:**
- [ ] A planned set (weight + reps filled, not completed) changes none of: volume, top set, progress
      point, export numbers, previous results (when the entry has a completed set), suggested weight.
- [ ] An entry with no completed sets still yields its sets with data as previous results.
- [ ] Warmup sets never affect volume, top set, progress points or suggested weight.
- [ ] `getSuggestedWeight` and `getSuggestedWeightInternal` return the same value for the same data.
- [ ] Tests for the above live at the new module's interface (node Jest); `npm test`, `npx tsc --noEmit`
      and `npm run build` pass.

**Out of scope:**
- Client-side completion checks (`completedCount`, "all done", finish-incomplete warning).
- SQL PR/progression functions (already completed-only).
- Planned-set generation on workout start, demo-mode mocks, and progression rules beyond the
  existing +2.5 kg.

### Resolution (2026-10-24)

Implemented as architecture candidate #1: `src/lib/setRules.ts` owns volume, top set, the
previous-results selection, suggested weight and the per-exercise summary, tested at its interface.
Progress graph, previous results, both suggested-weight variants and the export now use it.
Not changed: the export still lists every work set (planned ones included) in its per-set notation.
